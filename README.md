# Mesh Network — рабочее дерево

Этот каталог — рабочее дерево из пяти git-репозиториев: корневой
`mesh-network-lint` (публичный, линт-конвейер всего дерева) и четыре сабмодуля —
ядро протокола, проверки на ПК и две прошивки.

| Путь | Репозиторий | Ветка | Что это |
|---|---|---|---|
| `.` | `mesh-network-lint` | `master` | Линт-конвейер: `Makefile`, `tools/clang_tidy.py`, `.clang-format`, `.clang-tidy`, `pyproject.toml` |
| `mesh-network-core/` | `mesh-network-core` | `main` | Ядро протокола: радио, meshcore (кадры, дедуп, флуд), mesh OTA, крипто, настройки NVS. Библиотека, своего PlatformIO нет |
| `mesh-network-tools/` | `mesh-network-tools` | `prod` | Все проверки на ПК: `selftest.py`, `mcselftest/`. Не собирается, запускается питоном |
| `meshcore-fork/` | `meshcore-fork` | `develop` | Прошивки Heltec V3 / V4.3: координатор, сенсорный узел, прошивальщик, BLE-компаньон. 11 окружений |
| `tdeck/` | `tdeck` | `prod` | Прошивка LilyGO T-Deck: цветной экран, клавиатура, SD, GPS, приложения. 1 окружение |

Собственные файлы, которые в корневой репозиторий не попадают (`.gitignore`):
`all.md`, `instruction.md`, `lint.md`, `.env`, `MeshCore/` (апстрим MeshCore — локальный
справочник для сравнения с форком, в сборках не участвует).

## Как ядро попадает в прошивки

Ядро подключено к обеим прошивкам **зависимостью PlatformIO по ссылке**:

```ini
lib_deps =
    symlink://../mesh-network-core
```

- Локально в сборку идёт **рабочее дерево** соседнего репозитория: коммит в ядро
  немедленно попадает в обе прошивки. По обычному пути PlatformIO скопировал бы
  библиотеку в `.pio/libdeps` и больше не обновлял — прошивка молча собиралась бы
  со старым ядром.
- CI рабочее дерево не видит: ядро выкачивается по тегу из `core.ref` (одна строка
  в корне прошивки, сейчас `v0.23.1`). Проверки пинятся отдельно — `tools.ref`
  (ветка `prod`, не тег: это решение владельца, push в `prod` меняет результат
  CI обеих прошивок сразу).
- `scripts/gen_version.py` предупреждает, если локальное ядро ушло вперёд пина,
  а `scripts/release.py` в этом случае **отказывается отправлять** прошивку:
  в Actions она соберётся по пину и упадёт.
- Порядок выпуска: тег ядра (в том же коммите поднят номер в `library.json`) →
  перевод `core.ref` обеих прошивок → отправка прошивок.

## Сборка прошивок

### Что нужно

- PlatformIO (`pip install platformio`), Python 3.11+ (для `gen_ca_bundle.py` — 3.13+);
- g++ (проверки на ПК), node — по желанию (проверка синтаксиса JS страницы);
- дерево собрано, как здесь: прошивка и ядро — соседние каталоги (это требует
  `symlink://../mesh-network-core`).

### meshcore-fork (Heltec)

11 окружений в `platformio.ini`; голый `pio run` собирает 5 из `default_envs`:
`heltec_v3_coordinator`, `heltec_v4_3_sensors`, `heltec_v4_3_companion`,
`heltec_v4_3_support`, `heltec_v3_support`. Остальные 6 — только по
`pio run -e <имя>`: `heltec_v4_3`, `heltec_v4_3_coordinator`, `heltec_v4_3_ssd1306`,
`heltec_v3`, `heltec_v3_sensors`, `generic_sx1262`.

Роли складываются из флагов сборки, а не из ветвлений кода:

- **координатор** — WiFi, MQTT, веб-страница OTA (порт 3232), NTP, автообновление;
- **сенсорный узел** — только радио (`SENSOR_NODE=1`);
- **прошивальщик** — WiFi + страница + раздача OTA-сессий узлам, до которых
  координатор не дотягивается;
- **компаньон** — сенсорный узел + BLE для телефонного приложения.

### tdeck (T-Deck)

Одно окружение: `pio run` в `tdeck/`.

### Что происходит при сборке

`platformio.ini` цепляет pre-/post-скрипты (в порядке их выполнения):

| Этап | meshcore-fork | tdeck |
|---|---|---|
| pre | `gen_web.py` → `web_assets.h` (страница `web/` сжата gzip'ом) | — |
| pre | `gen_version.py` → `build_info.h`, обновление `version.txt` | `gen_version.py` |
| post | — | `build_apps.py` → пересборка приложений (ниже) |
| post | `copy_firmware.py` → образ в `firmware_output/` + git-коммит | `copy_firmware.py` |

**Версионирование.** `version.txt` — три строки: версия, хэш исходников и unix-время.
Хэш — SHA1 по исходникам прошивки **и ядра**: без ядра правка в нём не поднимала бы
номер сборки, `.otaz` перезаписывался бы под тем же именем, а автообновление считало
узлы актуальными. `gen_version.py` поднимает `BUILD` при смене хэша; счётчик
двузначный по правилу владельца: `0.5.99` → `0.6.1`. Несобранный релиз помечается
суффиксом `dev` в `build_info.h` (в `version.txt` номер без суффикса).

**Образы.** Сенсорные окружения упаковываются в `.otaz`:
`[OTAZ][размер 4B LE][CRC32 4B LE][zlib]` (формат описан в
`mesh-network-core/include/config.h`); координатор — голый `.bin`.
Автообновление ищет файл в релизе по имени `<окружение>_v<версия>`.

**Git после каждой сборки.** `copy_firmware.py` вызывает `scripts/release.py`:
коммит изменений и push рабочей ветки. Это поведение по умолчанию и **не** релиз.
Выключается: `NOGIT=1` (обязательно в CI — push оттуда перезапустил бы workflow,
то есть петля), `GIT=0` (разовая сборка). В коммит попадают только правки
отслеживаемых файлов и новые файлы из белого списка `ALLOW_NEW`; `FORBIDDEN`
(`secrets.json`, `.env`, `firmware_output/`, `build_info.h` и т.п.) роняет коммит.

**TLS-корни автообновления** — `scripts/gen_ca_bundle.py` (запускать вручную,
Python 3.13+): берёт корни из хранилища **локальной машины** и складывает в
`ca_bundle.h` (в git). За перехватывающим прокси в набор уедет корень прокси —
скрипт печатает имена корней, их надо посмотреть. Аварийный выход на устройстве:
`set tls_check 0`.

### Релиз

Релизом считается только push ветки `release/v<версия>` — её появление запускает
выкладку в Actions:

```
cd meshcore-fork    # или tdeck
RELEASE=1 pio run
```

`release.py --release` создаёт ветку, CI собирает её (проверки + сборка), и только
если всё прошло — ставит тег `v<версия>` и создаёт GitHub Release с файлами.
Уборка держит последние 5 релизов и 5 веток `release/*` (теги сохраняются).
Ядро так не выпускается: его тег ставится вручную, номер в `library.json`
поднимается в том же коммите, что тегируется.

## Сборка приложений T-Deck

Приложения не входят в образ прошивки: каждое — отдельный ELF (DSO), который
загрузчик прошивки (`tdeck_elf.cpp`, `tdeck_symtab.cpp`) релоцирует и связывает
по экспортной таблице, живущей в прошивке.

```
tdeck/apps/<имя>/
    setting.json    имя, версия, файл кода
    <имя>.cpp       код
    <имя>.h         интерфейс (АБИ — tdeck_api.h)
    <имя>.txt       данные приложения (попадают в пакет)
```

- `scripts/build_app.py` компилирует приложение **теми же флагами и заголовками,
  что прошивка**: команду берёт из `compile_commands.json` (поэтому в CI
  `pio run -t compiledb` идёт **до** `pio run`). Линк:
  `-shared -fno-pic -nostdlib -T apps/app.ld`; скрипт сразу проверяет, что в ELF
  нет релокаций и символов, которые загрузчик не умеет.
- `scripts/build_apps.py` (post-действие сборки) пересобирает все приложения
  при каждой сборке прошивки: таблица экспорта в прошивке, и приложение,
  собранное против прежней, после обновления может не загрузиться. Код не
  менялся — ELF выходит байт в байт прежним, версия не бампается, в git ничего
  не появляется. Выключить на разовую сборку: `NOAPPS=1`.
- Упаковка — `scripts/mkapp.py`: пакет `.tapp` =
  `[TAPP][размер 4B LE][CRC32 4B LE][zlib(tar)]`, внутри tar с одной папкой
  верхнего уровня. Пакеты складываются в `apps/completed/` (gitignored;
  готовые `.elf` в репозитории остаются — с чистого клона `mkapp.py --all`
  пакует именно по ним).
- На устройство пакет попадает на карту в `/apps/<имя>/` (распаковка — и есть
  установка) либо по эфиру с координатора (`/apps/save` + `/ota/start?kind=app`,
  приём — хуки ядра `mcOtaDataBegin/Write/Apply/Abort`).
- Хостовый предпросмотр экрана: `tdeck/host_render/` — `make` собирает рендер
  настоящего `tdeck_ui_draw.cpp` и настоящего кода приложений в PNG-кадры;
  CI кладёт кадры в артефакты.

## Проверки на ПК

Все проверки — в `mesh-network-tools` (ядро у прошивок общее, поэтому проверки
ядра не живут в потребителе):

```
cd mesh-network-tools
python3 selftest.py --target fork     # прошивки Heltec
python3 selftest.py --target tdeck    # T-Deck
python3 selftest.py --target core     # только ядро
python3 selftest.py --target all      # все цели подряд
```

Проверки вырезают настоящие функции из исходников, собирают их хостовым g++
с санитайзерами и гоняют на граничных данных; сверяют форматы, которые читает
устройство (`.otaz`, `.tapp`, шапку ELF, маркер платы в образе), и кросс-репозиторные
связи (пины, охват линта, наличие CI, секреты, расхождения копий `lib/meshcore`).
Обёртки на три строки `scripts/selftest.py` в прошивках запускают тот же
запускатель со своей целью.

## Линт-конвейер

Один на всё дерево, живёт в корневом репозитории; CI прошивок зовёт те же цели
`make`.

| Цель | Чем | Охват |
|---|---|---|
| `make lint-cpp` | clang-tidy через `tools/clang_tidy.py` (разбирает код как целевой компилятор, а не хостовый) | ядро + оба `lib/meshcore` + `tdeck/src` + `tdeck/apps`, минус сгенерированные заголовки; замечания печатаются, сборку не валят (решение) |
| `make format-cpp` / `format-cpp-check` | clang-format с PATH | то же |
| `make lint-py` | `ruff check` | `PY_DIRS_ALL` (tools, `scripts/` обеих прошивок, `tdeck/host_render`, `tools/`), отфильтровано `$(wildcard)` — в CI рядом с корнем лежит ровно одна прошивка |
| `make format-py` / `format-py-check` | `ruff format` | то же |

`pre-commit`: в корне — ruff check + format, в прошивках — clang-format.
Смотреть в выводе `lint-cpp` надо на `clang-diagnostic-error`
(`make lint-cpp | grep clang-diagnostic-error`): остальное — справочный шум.

## CI

| Репозиторий | Workflow | Что делает |
|---|---|---|
| корень | `lint.yml` | `make lint-py` + `make format-py-check` **без** сабмодулей: проверяется, что конвейер переживает дерево, где рядом нет прошивок |
| ядро | `checks.yml` | `selftest --target core` + задание `consumers`: собирает обеих потребителей против **этого** коммита ядра (приватный tdeck — deploy key только на чтение) |
| tools | `checks.yml` | `selftest --target core` + проверка связности набора проверок |
| fork | `build.yml` | checkout корня + прошивки + ядра (по `core.ref`) + проверок (по `tools.ref`); линт, selftest, `pio run` (default_envs, `NOGIT=1`), clang-tidy, артефакты; на `release/v*` — тег + релиз с файлами, уборка до пяти свежих |
| tdeck | `build.yml` | то же + `pio run -t compiledb` **до** сборки (нужна приложениям) и сборка предпросмотра экрана, кадры — в артефакты |

## Полезные команды

```
# все проверки
cd mesh-network-tools && python3 selftest.py --target all

# сборка обеих прошивок (окружения по умолчанию)
cd meshcore-fork && pio run
cd tdeck && pio run

# все 6 окружений форка, которых нет в default_envs
cd meshcore-fork && pio run -e heltec_v4_3 -e heltec_v4_3_coordinator -e heltec_v4_3_ssd1306 \
    -e heltec_v3 -e heltec_v3_sensors -e generic_sx1262

# линт и проверка форматирования
make lint && make format-check

# сборка без git
GIT=0 pio run

# база компиляции для clang-tidy и пересборки приложений
cd tdeck && pio run -t compiledb && pio run
```
